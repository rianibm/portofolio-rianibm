## A little context

Perkantas Yogyakarta is a community web platform supporting Christian discipleship activities for students, alumni, and medical professionals.

## Three decisions when returning to a live product

### 1. Stabilize before expanding the migration

The platform was already supporting everyday community tasks. I started with fixes and stabilization before broader migration work, using the UX audit and maintenance needs to guide the phase.

**Trade-off:** This puts less visible work ahead of a broader interface update. It also makes existing behavior and compatibility part of the delivery decision.

### 2. Refactor repeated interfaces for the next phase

The initial frontend used Laravel Blade and Bootstrap. In 2026, I refactored interfaces with Tailwind CSS and prepared components for API-based integration.

**Trade-off:** Existing pages and newer patterns had to coexist during the transition. Reusable layouts helped organize repeated interfaces while compatibility checks remained necessary. API-ready components describe the work delivered here; they do not imply that every migration was completed.

### 3. Verify CMS changes alongside API integration

A concrete verification target was CMS CRUD functionality: creating, reading, updating, and deleting content. I performed unit testing for those operations and collaborated with QA on regression checks and API validation, alongside database and deployment work.

This connects the migration work to behavior the platform still needed to support. The available record does not include a specific defect or test-result artifact, so I cannot show a verified before/after for those operations.

**Evidence boundary:** These checks support technical verification of the changes. They do not establish that community tasks became faster or easier; that requires separate user evaluation.

## Outcome

The 2026 work brought refactored interfaces, updated dependencies, and API-ready components, alongside database work and deployment support.

Technical checks supported the delivery; task-completion, support-volume, and satisfaction changes have not been measured.

## Learnings and next steps

Returning to my first freelance project changed the unit of responsibility: a page also has dependencies, data, and a deployment path to maintain. The 2026 phase required revisiting earlier decisions with the client and sequencing fixes before migration work.

Next, I would select an everyday community task and compare completion, points of hesitation, and requests for help. That would connect the technical modernization to evidence about the experience people actually use.
